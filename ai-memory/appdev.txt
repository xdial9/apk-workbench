2. ANDROID PLATFORM MENTAL MODEL (what the analyzer must reason about)
--------------------------------------------------------------------------------
APPLICATIONS RUN AS PROCESSES WITH COMPONENTS; the OS launches components via
Intents and holds a registry of them (from the manifest at install time).
Static analysis must reconstruct what the registry exposes because the OS
already trusts it: exported components = the OS will start them with
attacker-supplied Intents. Key mechanics:
- Components: activity (UI), service (background work, may outlive UI),
  broadcast receiver (listen for events), content provider (IPC data store
  with URI authorities), plus aliases of activities. Their correctness and
  exposure depend on manifest attributes.
- Intents: explicit (component named) or implicit (action + data + categories
  resolved against manifest filters). Deep links = implicit intents with
  data URIs (scheme[://host][:port][/path]). autoVerify = App Links.
- IPC surfaces: Binder via AIDL (services/providers), ContentProvider URIs
  (authorities), broadcast receivers with protected broadcasts.
- Permissions: install-time (normal/dangerous/signature) vs runtime grants
  (BCM 23+ for dangerous). <uses-permission> is a REQUEST (potentiality); a
  runtime grant is not visible statically — write it as request + usage
  evidence, never as granted.
- Package visibility (API 30+): <queries> gates what packages may be seen;
  missing visibility can break behavior — a portability hint not a vuln.
- Multi-user/work-profile: sharedUserIds are deprecated but still expose
  cross-app identity risk; not common — record, don't chase.
- Sandbox model: per-UID; data dirs are private unless surfaced (provider,
  export, world-readable legacy, backups, component exposure). This is the
  essential lens: any data leaving the sandbox = finding candidate.

3. BUILD & RELEASE PIPELINE (what produces what lands in the APK)
================================================================================
- Gradle: build.gradle(.kts) settings and variants; the APK is the manifest
  of these decisions: versionCode/versionName/min/target SDKs, signing config
  (keyAlias), flavor-specific paths/files inherited into the artifact. We
  DON'T see gradle files in APK but we see their effects.
- minifyEnabled + shrinkResources + proguard-rules.pro shape release output:
  obfuscated names (a.a.b), stripped symbols, inlined constants, string
  pool bubbling to res/strings.
- Dependencies: every declared gradle dependency gets merged into dex +
  res + assets. IMPACT: dependency inventory can be derived by package ROOT
  name histograms (group com.x.y): build the catalogue of 2nd-level
  packages; anything outside the platform/first-party list is a
  third-party candidate. This is DATA-DRIVEN (don't rely only on curated
  marker list; extend markers as hints but don't stop there).
- App Bundles (AAB) and Play delivery: the Play store splits into
  base.apk + config.<abi|density|locale> APKs + feature modules. Our
  acquisition already captures full bundles (APK + OBB); Phase B needs to
  accept asset-pack delivery components too (our current downloader rejects
  them — VERIFY google_play.py inspect: rejects non-.apk/.obb). This means
  the base.apk alone may NOT contain full behavior: feature modules are
  separate APKs. Surface must record which bundle members were NOT part of
  base.apk (bundle metadata exists at downloads/<pkg>-<ver>/google-
  play-bundle.json — read it for provenance rather than guessing).
- Multi-dex: classes.dex + classes2.dex..classesN.dex; unknown files may
  may be delayed/packed (packers keep the real dex as a blob in assets/libs).
- Signing: v1 (JAR, META-INF/*.SF/.RSA), v2/v3 (APK Signing Block), v4
  (tree). Signer identity is our provenance anchor (already captured at
  inspect — surface facts should carry it through).
- The developer's secrets-injection channel: CI injects into BuildConfig
  constants (public final static String) -> smali const-string. Values also
  creep into res/values/strings.xml via gradle resValue or manifest
  placeholders -> meta-data. BOTH places must be swept (they are).

4. APK ANATOMY — exact extraction checklist (per member)
================================================================================
- AndroidManifest.xml: binary XML in the zip; decoded by apktool. All facts
  per §7 below (manifest v2 parser).
- classes.dex + classes2.dex..N: dalvik bytecode. apktool exits into smali
  tree root/smali[-name]/... . androguard reads the ORIGINAL APK's dex.
  Every dex member belongs in surface's zip inventory.
- resources.arsc: compiled resource VALUE registry. apktool rebuilds res/.
  Do not parse ourselves; use decoded outputs; fall back to binary member
  hash in inventory.
- res/: decoded tree. Values worth more than names: strings.xml (keys +
  values — secret hints), arrays, xml/ (NSC, backup rules, provider paths),
  layout/.xml (password/input fields feature hints, known attributes like
  android:password or inputType=textPassword), drawable names (branding
  vocabulary), raw/ contents (arbitrary files), menu/, navigation.
- assets/: VERBATIM developer files. KEY: nobody obfuscates assets. Parse
  text (sniff), detect nested archives (.zip/.jar/.apk/.dex), .so blobs
  (packed code), sqlite DBs, JSON/YAML/property configs, HTML/JS bundles
  (Flutter libapp.so/assets, RN index.android.bundle (Hermes bytecode -
  detect magic, don't text-garbage-scan), Cordova www/ JS).
- META-INF/: MANIFEST.MF, *.SF, *.RSA (.DSA/.EC) — v1 signature presence +
  cert identity hints (CN/O strings are inspectable text). With v2-only
  apps META-INF may be absent — record where identity came from (Play
  signer set is authoritative at inspect).
- lib/<abi>/*.so: native code. Extract: symbol names (nm/objdump via
  subprocess wherever needed), embedded strings (strings-equivalent scan in
  our python), Java_ prefixed JNI symbols = exported native surface,
  packer signatures (blob && encrypted sections — generic hints only).
- APK Signing Block: not decoded; member hash suffices.
- kotlin metadata (META-INF/*.kotlin_module + in-dex annotations): can reveal
  renamed param names/classes; low priority, inventory-only.
- INSTALL-time extras: stamp files/junk from toolchains: record as
  toolchain artifacts, keep in inventory (invisible-elsewhere hints).

5. DEX/SMALI — SYNTAX + RECOGNITION SHAPES (recall sheet; risk of drift)
================================================================================
Smali essentials (verify with a real decoded file before relying):
- classes are dirs/files: com/foo/Bar.smali; header: .class public final
  Lcom/foo/Bar; -> .super Ljava/lang/Object; .source "Bar.java".
- fields: .field public static final API_KEY:Ljava/lang/String; = "abc"
- methods: .method public onCreate(Landroid/os/Bundle;)V ... .end method
- strings: const-string v1, "literal text" (b64/URLs/keys live here);
  const-string/jumbo for >64KB pool entries.
- invokes: invoke-virtual {v0, v1}, Lcom/x/A;->m(Ljava/lang/String;)V;
  variants: invoke-static, invoke-super, invoke-direct, invoke-interface,
  invoke-custom, invoke-polymorphic.
- annotations: inside methods/fields: .annotation [runtime] Lretrofit2/http/GET;
  value = "endpoint/path" ... .end annotation. RETROFIT: interface methods
  with @GET/@POST carry value = path; BaseUrl is a const-string near
  Retrofit.Builder().baseUrl("https://host/") mostly http scheme literal.
- line info: .line N — CRITICAL for evidence (our file:line cites from smali
  need line numbers; KEEP BUILD DEBUG INFO: we decode WITH debug info (we do
  not pass --no-debug-info). VERIFY these smali shapes against real decode
  output once in S-a (protect against version/decoder drift).
- R8 renaming shapes: short classes a, b, c inside top-level packages;
  fields a/b/c; packages collapsed (com.app. -> a.a. with map absent).
  My obfuscation heuristic must be a DEDUCED metric (ratio of 1-2 char
  names to total in code-owned packages) — never claim without a ratio.

Known smali fingerprints worth coding as markers:
- OkHttp client usage: Lcom/squareup/okhttp3/... ; interceptor chains.
- Retrofit: Lretrofit2/Retrofit; + .annotation Lretrofit2/http/GET;
- Firebase messaging: Lcom/google/firebase/messaging/FirebaseMessagingService;
- Room/SQLite: Landroidx/room/... + rawQuery or ROOM_SQL constants.
- JWT/token: classes manipulating Jwt / Auth or base64 decode chains.
- Ad SDK classes: Lcom/google/ads/... etc. (markers list, extendable).

10. HIDING CATEGORIES — obfuscation/packing/encryption taxonomy
================================================================================
- R8/ProGuard: class/method renames; no string encryption by default.
- DexGuard/custom string encryption: const-string replaced by decrypt-on-use
  blobs -> hint: heavy base64/hex literals + Cipher in same class.
- Packers: visible stub + packed real dex in assets/ (or .so) loaded via
  DexClassLoader; indicators: tiny visible app code + DexClassLoader +
  large binary assets + native unzipping. Record packer presence as a
  TOP-TIER context finding ("packed — visibility limited") since it downranks
  the reliability of all other facts for THIS member.
- Runtime-dynamic endpoints: RemoteConfig/AB/test links; only class hints.
- Multi-scheme deep-link hijacks; file provider paths with ../ coverage.
- Certificates: local pinned keys, user CA trust acceptance (allow user
  CA to MITM) — a config class fact.
- Language-level hiding: reflection (Class.forName on concatenation),
  MethodHandles/anonymous classes.

================================================================================
13. FACTS DATA MODEL + DEDUP LAW
================================================================================
- Fact = (kind, normalized_value, fingerprint=sha256(normalized_value),
  evidence[list of {path, line?, snippet?}], first_seen_path, count).
  Dedup: identical fingerprint merges; counts aggregate; representative
  evidence = first 3; full evidence kept in per-artifact evidence file but
  summary caps at 3 occurrences in dossier. New endpoints/values always
  fingerprint-normalized (URL decomposition: scheme+host+port+path).
- Deduction = (template_id, inputs[fingerprints], narrative, confidence,
  evidence chains). A deduction without cited input fingerprints is
  FORBIDDEN (deduce-not-guess doctrine).
- Coverage ledger: per-content-class + per-file route decision (scanned/
  skipped-binary/undecodable/packed). "Given evidence of skipped areas,
  state them in dossier's unknowns."
- Confidence scale: tool_verified / deduced / hint ; each carries severity
  as interpretation only (never pretends runtime proof).

16. DRIFT TRIPWIRES (my known failure modes -> countermeasure)
--------------------------------------------------------------------------------
1. Confident specifics (smali syntax, schema fields): VERIFY against real
   decoded output/fixtures before coding. In file work only memorize what
   fixtures have shown.
2. Schema breakage: changing inventory/findings fields w/o updating §15
   consumers = cross-cutting breakage — always map change -> consumers
   first (checklist per edit).
3. Non-determinism: avoid sets for ordering (sort everywhere); sort
   evidence lists; stable dict ordering (insertion) everywhere; stable
   temp-file names; datetime formats.
4. Regex drift: keep case-sensitivity explicit per rule; unify IGNORECASE
   policy in one place (a compilation table), not per call site.
5. Memory bloat: avoid whole-file lower casing (1C.7); avoid oversized
   snippets; keep evidence capped in summary but complete on disk.
6. Fatigue drift: scope creep / rewriting entire modules mid-item — STOP,
   re-read plan.txt phase boundaries, itemize changes, get discipline
   back with a checklist before next edit.
7. Progress silence: always respect <=2s heartbeat (Appendix D); long
   units emit sub-progress (chunk/method counts).
8. Losing tests green: run pytest after each small change; never batch
   multiple behavior changes without running.
9. Hallucinated file:line references in narratives: cite ONLY pointers
   that the code produced in the same run (never from memory).
10. Scope: surface.txt (S-a..S-g) governs surface work; if an edit seems
   needed elsewhere, note it in §14 and CONTINUE S, don't drift.
